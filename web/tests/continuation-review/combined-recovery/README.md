# Recovery storage, staged only

New module copies combined-storage's guarded save/load policy and adds read-only discovery/export. It is staged only into root-wind-recovery; earlier artifact source is unchanged. Restore is intentionally not implemented until a guarded native capture/apply contract is frozen.

`listBackups()` enumerates strict canonical pre-v7/pre-v13, pre-v13 SHA256 and world.recovery SHA256 filenames in /wetlands-saves only. Staging/current/world files are excluded. Each valid row includes name/version/size/SHA256. Corrupt entries remain visible as invalid with a reason; they cannot be exported. A file must be regular, 1..128MiB, valid UTF8 JSON with integer version1..10 or13. This is not full native schema validation. Hash filenames and caller's selected hash must match exact current bytes, rechecked after hashing. No native calls or writes occur. `exportBackup(name,sha256)` returns verified bytes for a UI download, not an implicit restore.

Five focused mocked-FS tests pass: persistent discovery through recreated storage, verified exact export, invalid/path/corruption/version/size/directory rejection, stale selection and read failures. No actual browser/IndexedDB claim. An initial preparer source-path typo and missing world.recovery prefix caused staging/test failures; both were corrected before acceptance. Existing frozen storage module is untouched.

## Guarded restore added

`restoreBackup(name,sha256)` is called only after UI confirmation. It owns storage busy state across all awaits. It verifies selected bytes, obtains the native paused/current-world preparation token and staged current save, verifies that receipt's size/hash/version, writes or verifies immutable `world.recovery.sha256-H.json`, reads it back, durably syncs and verifies again. Selected bytes/hash and writer identity are rechecked before the single native apply call. The native API independently verifies full current-state hash, selected file and current checkpoint. Finally the token is canceled if still present. The canonical `world.json` is never written: restoring changes the in-memory world only, with explicit later Save required. Existing matching checkpoints are resynced, never treated as already durable merely because present.

Eleven focused mocked-FS tests pass, covering readable discovery/export plus successful restore order, staged/current/selected corruption, size/receipt errors, quota/write/readback/read failure, stale identity/target, all native refusal codes, immutable checkpoint collision/dedup and repeated busy clicks. `lastRecoveryError` preserves precise actionable reason. Thrown/unknown native apply results are labeled uncertain, not claimed unchanged. Native atomic refusal semantics need the independent native gate; these tests do not substitute for it. The first copied regression run passed two suites but failed the obsolete “automatic restore is not available” copy assertion. The failed log is retained; the recovery-only adapter now checks the required Recovery backups wording, with all behavioral assertions unchanged. UI confirmation/cancel belongs to the separate controller tests; storage does not ask its own duplicate confirmation.

Final composed gate: all12 focused tests and all3 copied regression suites pass. The added test uses the actual `combined-recovery.js` controller with the actual storage implementation and mock FS: discover/select/cancel makes no preparation call; confirmed success syncs the exact current-world checkpoint before native apply; quota failure prevents apply and preserves live/canonical state. Pause-required error is explicitly exposed through lastRecoveryError. The original regression-failure log remains alongside final passing log.

### Failed-save dirty-slot guard

Recovery now refuses before any verification/preparation/sync after an unsuccessful Save, because IDBFS sync flushes the whole mount and could otherwise commit a dirty in-memory canonical file left by the failed Save. The error requires a successful Save or page reload and warns that reload loses unsaved active progress. The failed-save flag survives busy/unavailable retries and clears only after successful durable Save. The explicit sequence test writes different canonical bytes in RAM, fails sync, verifies recovery makes no further native/sync calls and changes neither RAM nor durable canonical, then permits recovery after a successful Save. All13 focused tests and3 copied suites pass. A first test-fixture attempt omitted FS.open/read/close needed by save-version inspection; the fixture was completed without changing production behavior.
