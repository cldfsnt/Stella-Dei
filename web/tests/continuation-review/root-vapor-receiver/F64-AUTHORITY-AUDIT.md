## Serialization and compatibility

`save_schema.Save.vapor` currently []constf32 (line139), shape validation150 and finite0..1e15 native mass225. `save_game.capture`35 references the array; apply75/80 copies both current and scratch arrays. F64 fields require versioned schema/native identity, validation and both arrays restored before simulation. Soil/root experimental schema10 is not live production6 and must not be silently reinterpreted.

**Old JSON must be parsed as old f32 first, then widened.** Merely changing Save.vapor to f64 may interpret a shortest f32 decimal string as a different real value (e.g.1.2), losing exact legacy bit semantics. Version-dispatch parsing must preserve the oldf32 rounding before widening. Newf64 values need exact roundtrip and cannot be accepted then silently truncated by older code. If storage remains native mass, f32→f64 widening itself is exact; converting to density adds an actual area/unit rounding boundary requiring its own input ledger. No inference from absent fields or hidden precision residual.

Migration remains explicit Save only; loading must not overwrite the existing canonical file. Preserve shared128MiB stream bound/atomic rename, old canonical on refusal, invalid-load atomicity, unsupported law/version rejection, Sandbox/Origin/newworld resets and no snapshotaliasing. Test actual legacy decimal edgecases, sameworld and changed-geometry uninterrupted-vs-restored continuation, empty/sparse/dense worlds, and new-format rejection by old readers. A format compatible reader does not establish identical new model trajectories.
